# 纯软件聚焦版真实平台设想

生成日期：2026-06-15

## 1. 重新定义范围

本项目现阶段不做完整医院工作流，也不做真实设备工作站。平台范围应收缩到口腔数字观察仪或离线双通道数据进入软件之后的后三层：

1. **荧光分析层**：对白光/ICG 双通道图像或帧序列进行配准、增强、定量和时间序列分析。
2. **AI 与医生交互判读层**：提供疑似区域、边界风险、阈值调节、ROI 标注、关键帧确认和医生复核。
3. **结果输出层**：输出关键截图、量化表、结构化报告、病例证据包，后续可扩展 DICOM secondary capture。

不作为本阶段重点：

- 患者信息管理。
- 医院 HIS/EMR/PACS 接入。
- 术前完整手术规划。
- 真实设备驱动和实时采集 SDK。
- 临床级自动诊断。

本阶段平台应是一个**纯软件的术中荧光辅助判读平台**，可使用离线图片、同步帧序列或模拟视频作为输入。

## 2. 推荐平台名称

推荐名称：

**颌骨骨髓炎术中荧光辅助判读软件平台**

更工程化名称：

**ICG-Fluorescence Surgical Interpretation Workbench for Jaw Osteomyelitis**

比赛展示表达：

**基于白光/ICG 双通道影像的颌骨骨髓炎术中边界风险提示与报告软件**

## 3. 核心医学逻辑

ICG 不能作为颌骨骨髓炎特异性诊断探针。软件平台的医学逻辑应建立在以下事实之上：

- ICG 主要反映血流灌注、血管通透性和组织活性差异。
- 坏死骨或严重低活性组织可能表现为低荧光或无荧光。
- 炎症、肉芽组织或血供丰富区域可能表现为高荧光。
- 单帧强度容易受曝光、距离、角度、组织反光和设备参数影响。
- 更有意义的是局部相对强度、区域强度比、时间-强度曲线和医生确认后的边界。

因此，输出应定位为：

- 低灌注提示。
- 异常荧光增强提示。
- 可疑坏死骨候选区。
- 边界不确定区。
- 医生复核建议区域。

不应输出：

- “确诊骨髓炎”。
- “自动决定切除边界”。
- “替代病理或医生判断”。

## 4. 输入形态

平台至少支持三类输入，从低复杂度到高复杂度：

### 4.1 单帧双通道输入

- 白光图像。
- 同视野 ICG 荧光图像。
- 可选元数据：曝光、增益、时间点、给药后分钟数。

用途：

- 比赛初版演示。
- 快速验证伪彩融合和 ROI 定量。

局限：

- 无法分析动态灌注。
- 对设备参数和单帧质量敏感。

### 4.2 同步帧序列输入

- 白光帧序列。
- ICG 荧光帧序列。
- 帧时间戳或帧序号。
- 可选给药时间点。

用途：

- 更接近真实术中场景。
- 可分析荧光增强、峰值和消退趋势。

### 4.3 视频输入

- 白光视频。
- 荧光视频。
- 或设备导出的双通道视频。

用途：

- 更适合展示“术中软件平台”形态。
- 可抽取关键帧、生成短片段和动态报告。

本阶段可先支持单帧和短序列，视频作为后续扩展。

## 5. 荧光分析层

### 5.1 通道校准和预处理

基础能力：

- 图像尺寸对齐。
- 白光/荧光通道配准。
- 荧光强度归一化。
- 噪声抑制。
- 过曝/欠曝提示。
- 黑场背景或无效区域裁剪。

可选增强：

- 基于特征点的刚性配准。
- 基于 ECC / optical flow 的局部配准。
- 显微镜视野边缘遮罩。
- 帧间稳定化。
- 亮度漂移校正。

### 5.2 伪彩融合

固定输出：

- 白光原图。
- 荧光灰度图。
- 伪彩热图。
- 白光+伪彩叠加图。
- 阈值掩码图。

可调参数：

- alpha 透明度。
- colormap。
- intensity window。
- threshold。
- gamma。
- ROI 内/外显示模式。

### 5.3 定量分析

单帧指标：

- mean intensity。
- max intensity。
- median intensity。
- p90 / p95 intensity。
- positive area px。
- positive area fraction。
- ROI/background ratio。
- suspicious area count。
- connected component area。

序列指标：

- time to enhancement。
- time to peak。
- peak intensity。
- wash-in slope。
- wash-out slope。
- area under curve。
- ROI/background dynamic ratio。
- low-perfusion duration。

### 5.4 风险图生成

风险图不等同于诊断图。建议分成三类：

- 低灌注风险图：强调低荧光或无荧光区域。
- 高荧光风险图：强调异常增强、炎症或高通透性候选区。
- 边界不确定图：强调阈值附近、变化不稳定或模型不一致区域。

## 6. AI 与医生交互判读层

### 6.1 AI 的合理任务

本阶段 AI 适合承担以下任务：

- 自动建议 ROI。
- 分割高荧光/低荧光区域。
- 提取边界候选线。
- 识别不稳定或模糊边界。
- 对帧序列进行关键帧选择。
- 检测明显伪影、过曝、低质量帧。
- 给出不确定性热图。

AI 不应承担：

- 独立诊断骨髓炎。
- 直接给出最终切除线。
- 在无真实标注时宣称临床准确率。

### 6.2 医生交互能力

核心交互：

- 手动画 ROI。
- 调整阈值。
- 切换 colormap。
- 确认关键帧。
- 标记“疑似坏死骨”“疑似炎症”“保留区”“不确定边界”。
- 添加文字备注。
- 接受或覆盖 AI 建议。

更真实的交互：

- 双视图对照：白光/荧光/叠加图同步缩放。
- 帧序列时间轴。
- ROI 强度曲线联动。
- 多 ROI 对比。
- 一键生成术中截图。
- 医生确认状态：未确认、已复核、已修正、排除。

### 6.3 结果状态设计

每个候选区域应有状态：

- `candidate`：AI 或阈值生成的候选。
- `review_required`：建议医生复核。
- `accepted`：医生接受。
- `modified`：医生修改。
- `rejected`：医生排除。

这种状态比单纯显示“阳性/阴性”更符合医学场景。

## 7. 结果输出层

### 7.1 报告内容

报告应包含：

- 输入文件摘要。
- 分析参数。
- 关键帧。
- 白光图、荧光图、融合图、风险图。
- ROI 定量表。
- 医生标注和备注。
- AI 建议区域状态。
- 免责声明。

### 7.2 输出格式

当前阶段：

- Markdown 报告。
- JSON 结构化报告。
- PNG/JPEG 关键图。
- CSV 量化表。

后续扩展：

- PDF 报告。
- DICOM secondary capture。
- DICOM SR。
- MP4 关键片段。
- ZIP 病例证据包。

### 7.3 结构化 JSON 建议字段

建议包含：

- `case_id`
- `input_channels`
- `acquisition_metadata`
- `fusion_parameters`
- `quality_flags`
- `roi_list`
- `quantification`
- `candidate_regions`
- `physician_review`
- `outputs`
- `disclaimer`

## 8. 技术栈选型

### 8.1 当前快速实现栈

- Python 3.11。
- Gradio：快速平台软件和比赛演示。
- NumPy / SciPy：强度分析和曲线计算。
- OpenCV：图像配准、视频帧处理、轮廓和阈值。
- Pillow：图像读写。
- matplotlib：曲线、热图和报告图。
- pandas：量化表和 CSV。
- pydicom：DICOM 扩展预留。
- PyTorch：AI 模型推理和训练。
- MONAI / nnU-Net：医学分割基线。
- pytest：测试。

### 8.2 更像工作站的前端栈

后续正式平台建议直接走前后端分离：

- 前端：TypeScript + Vue 3 + Vite。
- 状态管理：Pinia。
- 路由：Vue Router。
- 组件库：Element Plus 或 Naive UI。
- 图像叠加：Canvas、WebGL 或基于 `<canvas>` 的图层系统。
- 曲线与统计：ECharts。
- 视频预览：原生 `video` 元素或轻量播放器封装。
- 后端：Python 3.11 + FastAPI。
- 推理与训练：PyTorch。
- 医学影像处理：OpenCV、SimpleITK、nibabel、pydicom。
- 异步任务：RQ、Celery 或 FastAPI background tasks。
- 运行存储：SQLite 起步，后续可切 PostgreSQL；文件结果保存在本地磁盘或对象存储。

选择建议：

- 比赛快速演示：Gradio 作为临时桥接层。
- 目标平台形态：Vue 前端 + Python API + PyTorch 推理后端。
- 桌面壳层仅在需要本地工作站感时再评估 Electron。

### 8.3 图像/视频处理扩展

- OpenCV：视频读取、帧处理、配准。
- scikit-image：形态学、轮廓、区域属性。
- SimpleITK：医学图像配准思路迁移。
- PyAV / ffmpeg：视频解码和导出。
- napari：医学图像和标注查看。

### 8.4 AI 模型可能性

不固定模型，但可列候选：

- 阈值 + 形态学：低成本 baseline。
- U-Net / UNet++：2D 荧光区域分割。
- nnU-Net：3D CBCT 结构分割基线。
- MedSAM / SAM2 / MedSAM2：交互式 ROI 标注。
- YOLO / RT-DETR：候选区检测。
- ConvNeXt / EfficientNet / ViT：图像级质量或风险分类。
- U-Mamba / MedNeXt：后续医学分割实验。
- MC Dropout / Test-time augmentation：不确定性提示。

### 8.5 数据可能性

本阶段可使用：

- 人工模拟白光/荧光样例。
- 公开荧光手术视频数据。
- MODID 多光谱口腔数据。
- D024 DentVoxel：CBCT 结构先验和 3D 分割验证。
- D025 牙源性病灶 CBCT：病灶相关验证。
- 后续企业/医院脱敏白光/ICG 样本。

## 9. 比赛版本建议

为了降低复杂度，比赛版建议只做：

1. 单帧双通道融合。
2. 小规模帧序列强度曲线。
3. ROI 手动画和阈值调节。
4. 低灌注/高荧光风险图。
5. AI 候选区作为可选增强。
6. Markdown/JSON/PNG 报告导出。

暂不做：

- 实时设备接入。
- 完整病例管理。
- PACS/HIS 集成。
- 自动诊断。
- 多医生协同平台。

## 10. 最小可信演示流程

推荐答辩演示流程：

1. 打开软件平台。
2. 选择一组白光/ICG 双通道样例。
3. 展示白光、荧光、伪彩叠加。
4. 调节阈值和透明度。
5. 手动画一个 ROI。
6. 展示 ROI 强度统计和风险图。
7. 标记一个“建议复核区域”。
8. 导出报告和关键截图。
9. 说明 ICG 是灌注/活性提示，最终由医生复核。

## 11. 更真实的使用场景

### 11.1 角色

- 主刀医生：确认可疑边界、调整阈值、决定是否接受 AI 建议。
- 术中助手：导入图像、选择关键帧、补充备注。
- 科研人员：回看病例、导出证据包、做批量统计。
- 平台管理员：配置模型、版本、报告模板和权限。

### 11.2 一次完整会话

1. 打开病例，导入白光与荧光帧或短视频。
2. 系统先做质控，检查是否存在无荧光、过曝、错位、模糊、时间戳异常。
3. 质控通过后进入融合视图，显示白光原图、荧光图、叠加图和风险图。
4. 医生圈定 ROI，系统同步计算均值、峰值、p95、阳性面积和区域比值。
5. AI 生成候选区域和不确定性热图，医生可接受、修正或排除。
6. 所有调整写入病例状态，形成可追溯的复核记录。
7. 会话结束时导出 Markdown、JSON、PNG、CSV，必要时再打包 MP4 和病例证据包。

### 11.3 界面应该长什么样

- 左侧：病例列表、输入通道、文件状态、任务进度。
- 中央：白光、荧光、叠加图三联视图，支持缩放、拖动、切换帧。
- 右侧：阈值、透明度、色图、ROI 列表、AI 建议、质控提示。
- 底部：时间轴、强度曲线、事件日志、导出按钮。

### 11.4 真实场景里的异常情况

- 荧光信号太弱，系统需要提示“当前帧参考价值有限”。
- 白光和荧光不同步，系统应把这类帧标成低可信。
- 组织反光、出血、烟雾、器械遮挡，都会污染判读。
- ROI 过小或位置不稳时，系统只给提示，不强行下结论。
- 医生和 AI 结论冲突时，以医生复核状态作为最终记录。

### 11.5 最终交付物

- 单病例报告：`report.md`。
- 结构化结果：`report.json`。
- 量化表：`quantification.csv`。
- 关键图：`overlay.png`、`heatmap.png`、`roi_mask.png`。
- 证据包：`evidence.zip`。
- 后续扩展：DICOM secondary capture、DICOM SR、视频摘要。

## 12. 真实平台的系统形态

这个平台更像一个本地部署的术中荧光判读工作台，核心不是“自动诊断”，而是“采集后分析 + 人机协作复核 + 病例归档”。

推荐的工程分层是：

1. 前端展示层：Vue 负责病例页、图像页、曲线页和报告页。
2. API 层：Python FastAPI 负责上传、任务派发、结果查询和导出。
3. 分析层：OpenCV、PyTorch、SimpleITK、pydicom 处理融合、量化和模型推理。
4. 存储层：本地文件系统 + 结构化元数据，后续可升级数据库与对象存储。
5. 任务层：异步队列处理视频、批量病例和模型推理。

这样设计的好处是：

- 可以先做纯软件 demo。
- 以后接真实设备时，只需替换输入源。
- 以后接更强模型时，只需替换分析层。
- 以后接医院系统时，只需补 API 和导出协议。
